# Contributing to zvec-go

Thank you for your interest in contributing to zvec-go! This guide covers the development workflow, project architecture, and best practices.

## Prerequisites

| Tool | Version | Purpose |
|------|---------|---------|
| Go | ≥ 1.21 | Go SDK development |
| C compiler | gcc / clang | cgo compilation |
| CMake | ≥ 3.20 | Building zvec C-API |
| Ninja | latest | CMake build backend |
| golangci-lint | latest | Go linting (optional) |

A C compiler is only required for the cgo backends. With `CGO_ENABLED=0` the SDK
builds against the purego/FFI backend instead — the zvec shared library is still
needed at runtime.

> **Windows ARM64**: cgo needs an ARM64-native MinGW toolchain
> (`aarch64-w64-windows-gnu`). The x86_64 `gcc` bundled with the `windows-11-arm`
> runner image cannot assemble Go's `runtime/cgo/gcc_arm64.S`. See *Supported
> Platforms* in [README.md](README.md) for the MSYS2 setup.

## Project Architecture

```
zvec-go/
├── zvec/                  # git submodule → github.com/alibaba/zvec
│   └── src/include/zvec/
│       └── c_api.h        # C-API header (the contract between zvec and zvec-go)
├── lib/                   # Vendor mode pre-built libraries (gitignored, generated)
├── cgo_vendor_*.go        # Vendor mode #cgo directives, one file per GOOS/GOARCH
├── cgo_source.go          # Source mode #cgo directives (Unix)
├── cgo_source_windows.go  # Source mode #cgo directives (Windows)
├── zvec.go                # Library initialization, version, config
├── collection.go          # Collection CRUD, insert/update/upsert/delete/query/fetch
├── doc.go                 # Document field operations
├── query.go               # VectorQuery, GroupByVectorQuery, query params (HNSW/IVF/Flat)
├── multi_query.go         # MultiQuery: composing sub-queries (hybrid search)
├── schema.go              # IndexParams, FieldSchema, CollectionSchema
├── types.go               # Go enum types (DataType, IndexType, MetricType, etc.)
├── errors.go              # Error handling, C→Go error conversion
├── fts.go                 # Full-text search query payload
├── iterator.go            # Document iterator
├── purego_loader.go       # FFI backend: dlopen, symbol registration, ABI gate
├── purego_api.go          # FFI backend: mirror of the cgo API surface
├── purego_call.go         # FFI backend: SyscallN argument/return wrappers
├── purego_unix.go         # FFI backend: Unix library path resolution
├── purego_windows.go      # FFI backend: Windows library path resolution
├── cmd/download-libs/     # Fetches pre-built libraries into lib/ (via go:generate)
├── scripts/
│   └── sync-zvec.sh       # Submodule sync with C-API change detection
│   └── package-libs.sh    # Build & package vendor libs + header into lib/
├── examples/              # Usage examples
├── Makefile               # Build, test, lint automation
└── .github/
    ├── workflows/ci.yml      # CI: source + vendor mode on 6 platforms
    ├── workflows/release.yml # Builds and publishes the pre-built lib/ archives
    └── dependabot.yml        # Auto-update submodule & GitHub Actions
```

### How the Bindings Are Wired

All `#cgo` directives live in dedicated files, **not** in the API files. That
separation is what lets one API surface link against either the pre-built or the
from-source library:

| File | Build tags | Links against |
|------|-----------|---------------|
| `cgo_vendor_{darwin,linux,windows}_{amd64,arm64}.go` | `cgo && !source && <goos> && <goarch> && !purego` | `lib/<goos>_<goarch>/` + `lib/include/` |
| `cgo_source.go` | `cgo && source && !windows && !purego` | `zvec/build/lib/` + `zvec/src/include/` |
| `cgo_source_windows.go` | `cgo && source && windows && !purego` | `zvec/build/lib/` + `zvec/src/include/` |

Source mode (`cgo_source.go`):

```go
/*
#cgo CFLAGS: -I${SRCDIR}/zvec/src/include
#cgo LDFLAGS: -L${SRCDIR}/zvec/build/lib -lzvec_c_api -Wl,-rpath,${SRCDIR}/zvec/build/lib
*/
import "C"
```

The API files (`zvec.go`, `collection.go`, `doc.go`, `query.go`, `multi_query.go`,
`schema.go`, `types.go`, `errors.go`, `fts.go`, `iterator.go`) are tagged
`//go:build cgo && !purego` and only `#include "zvec/c_api.h"` — they never carry
`#cgo` flags.

- **CFLAGS**: Points at the C-API header (submodule, or `lib/include` in vendor mode)
- **LDFLAGS**: Links against `libzvec_c_api`
- **rpath**: Ensures the dynamic linker finds the library at runtime

`lib/` is **not** committed and does **not** use Git LFS (see `.gitignore` and
`.gitattributes`). It is generated by `go generate ./...`, which runs
`cmd/download-libs` to fetch the pre-built archive for the current platform from
GitHub Releases.

### The purego (FFI) Backend

The same API surface is available without a C compiler, selected automatically by
`CGO_ENABLED=0` (or forced with `-tags purego`):

| File | Role |
|------|------|
| `purego_loader.go` | Loads the shared library, registers every symbol into `zvecPuregoAPI`, enforces the ABI gate (`puregoABIMajor` / `puregoABIMinor` / `puregoMinABIPatch`) |
| `purego_api.go` | Mirror of the cgo API surface (`//go:build purego \|\| !cgo`) |
| `purego_call.go` | `purego.SyscallN` argument and return wrappers |
| `purego_unix.go`, `purego_windows.go` | Library path resolution (`ZVEC_LIBRARY_PATH`, then SDK/executable-relative defaults) |

## Getting Started

```bash
# 1. Clone with submodules
git clone --recursive https://github.com/zvec-ai/zvec-go.git
cd zvec-go

# 2. Build the C-API library
make build-zvec

# 3. Run tests
make test

# 4. Run linter
make lint
```

## Development Workflow

### Daily Development

```bash
# Build + test in one command
make all

# Run tests with verbose output
make test

# Run benchmarks
make bench

# Check code quality
make lint

# Format code
make fmt
```

### When zvec Has C-API Changes

The zvec C-API header (`zvec/src/include/zvec/c_api.h`) is the contract between zvec and zvec-go. When it changes, Go bindings may need updates.

#### Step 1: Check for Changes

```bash
# Check if upstream has C-API changes (without updating)
./scripts/sync-zvec.sh --check-only
```

#### Step 2: Update and Verify

```bash
# Update submodule + rebuild + test
./scripts/sync-zvec.sh --build

# Or update to a specific version
./scripts/sync-zvec.sh v0.8.0 --build
```

#### Step 3: Update Go Bindings (if needed)

If the script reports C-API changes, review the diff and update the corresponding Go files:

| C-API Area | Go File | What to Update |
|------------|---------|----------------|
| `zvec_initialize`, `zvec_shutdown`, `zvec_config_*` | `zvec.go` | Init/config functions |
| `zvec_collection_*` | `collection.go` | Collection operations |
| `zvec_doc_*` | `doc.go` | Document field operations |
| `zvec_vector_query_*`, `zvec_*_query_params_*` | `query.go` | Query types and params |
| `zvec_*_schema_*`, `zvec_index_params_*` | `schema.go` | Schema and index params |
| `zvec_error_code_t` enum values | `errors.go` | Error codes |
| `zvec_data_type_t`, `zvec_index_type_t`, etc. | `types.go` | Enum constants |

#### Step 4: Commit

```bash
git add zvec
git commit -m "chore(deps): update zvec submodule to <version>"
```

### Automated Updates via Dependabot

Dependabot is configured to automatically create PRs when:
- The zvec submodule has new commits (weekly check)
- GitHub Actions have new versions

These PRs will trigger CI, which builds the C-API and runs all tests.

## Adding New C-API Bindings

When a new function is added to `c_api.h`, follow this pattern:

```go
// 1. Add the Go wrapper function with proper documentation
// FunctionName does something useful.
func FunctionName(param string) error {
    // 2. Convert Go types to C types
    cParam := C.CString(param)
    defer C.free(unsafe.Pointer(cParam))

    // 3. Call the C function and convert the error
    return toError(C.zvec_function_name(cParam))
}
```

Key conventions:
- **Always** use `toError()` to convert C error codes
- **Always** free C strings with `defer C.free(unsafe.Pointer(...))`
- **Always** check for nil handles before operations
- Use `unsafe.Slice()` for converting C arrays to Go slices
- Transfer ownership explicitly (set handle to nil after transfer)

### Mirror the Change in the purego Backend

The cgo wrapper above only covers `CGO_ENABLED=1`. For the same symbol:

1. Add a field to `zvecPuregoAPI` in `purego_loader.go` and register it next to the
   related symbols: `register(&puregoFns.functionName, "zvec_function_name")`.
2. Implement the counterpart in `purego_api.go`, reusing the wrappers in
   `purego_call.go`.
3. If the C-API moved to a new minor version, raise `puregoABIMinor` in
   `purego_loader.go` so the loader rejects an older library with a clear message
   instead of failing on a missing symbol.
4. When upstream **removes** a symbol, delete it from both backends — a stale
   `register()` call makes the purego loader fail at init.

## Code Style

- Follow standard Go conventions (`gofmt`, `go vet`)
- Use descriptive variable names (no single-letter names)
- Add godoc comments to all exported types and functions
- Keep cgo blocks minimal — put Go logic outside `import "C"` blocks
- Use `//go:build integration` tag for tests that require the C library

## Running CI Locally

```bash
# Source mode: build the C-API from the submodule, then test/bench/lint
make clean build-zvec test bench lint

# purego backend against that same library (no C compiler involved)
# (libzvec_c_api.so on Linux, .dll on Windows)
CGO_ENABLED=0 ZVEC_LIBRARY_PATH=$PWD/zvec/build/lib/libzvec_c_api.dylib \
  go test -tags integration -count=1 .

# Vendor mode: fetch the released pre-built libraries, build without -tags source
go generate ./...
CGO_ENABLED=1 go test -tags integration -count=1 ./...
```

CI runs source and vendor mode on six platforms — macOS x64/ARM64, Linux
x64/ARM64, Windows x64/ARM64. The purego suite runs in the source-mode jobs.
See `.github/workflows/ci.yml`.
